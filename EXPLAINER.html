Rodada 4 em destaque

O comando da rodada foi “no-stop + feedback denso”: dark ruim, bug B1 (list-challenges), bug B2 (DeepSeek sem content), tutorial que não imitava o Ondokai, tela inicial pouco clara, input/botão diferentes, UX a pesquisar e refazer, mais E2E com chaves reais, e matemática/LaTeX. Quatro ondas resolveram isso.

Bug B2 · DeepSeek sem content — causa-raiz provada

O sintoma na tela era um erro enganoso:
sem choices[0].message.content. A causa verdadeira estava um passo antes, no HTTP status code.

Caminho crítico

O leitor experiente pula as caixas vermelhas: o essencial é que um HTTP 400 (requisição rejeitada pela API) era engolido pelo cliente porque ele só sabia tratar 401/403/429/5xx. Como 400 não encaixava em nenhum tratamento, o código seguia como “sucesso” até choices[0] não existir e produzir o erro enganoso. A prova da causa foi feita na API real, com a sua chave: o id …-0731 devolvia 400; o id validado deepseek-v4-flash devolveu 200.

Bug B1 · list-challenges “requer setupRoot”

Frase do usuário: “list-challenges: setupRoot not found — requer setupRoot”. O valor era gerado corretamente na aula, mas não fluía até o desafio.

Definições inline. setupRoot = o diretório de trabalho de uma aula (um workspace, raiz do “setup”) onde os arquivos do desafio são preparados e testados. orchestrator = o processo central que divide o fluxo “gerar aula → listar desafios → rodar testes” e emite eventos de progresso pelos canais. IPC = Inter‑Process Communication, o canal main(processo Node)⇄renderer(React) do Electron.

→ caminho crítico sinalizado no texto

O ponto que resolveu o bug foi o orchestrator emitir progresso materializing carregando setupRoot/setupId; o handler gravou isso na memória, e a UI (contexto ChallengeNav) passou a entregar {setupRoot} explícito à ChallengeView. O revisor ainda exigiu reset do lastSetupRoot em novo generate e effect de listagem com dependência correta.

W16 · Tutorial refeito fiel ao Ondokai

O onboarding parou de ser um tour informativo e virou um sistema de spotlight real: overlay, máscara, 2 tutoriais, avaliação por snapshot e narração local.

Os 2 tutoriais

  • Tutorial Completo — ~13 passos; cobre a jornada inteira (configurar chaves, aula, desafio, editor, teste).
  • Quick Start — ~6 passos; vai direto ao essencial para o usuário que quer começar logo.
  • Modal de seleção com gate de chaves (Completo) e CTA Configurar chaves.

Avaliação e reforço

  • Snapshot: estado da UI num instante; 8 expectedActions esperados por passo (função pura evaluateStepAction).
  • Dead-lock corrigido: alvo ausente é saltado com fallback Continuar.
  • Hint pós-tutorial de 1x apontando o input de assunto; TTS local Piper narra cada passo.
  • i18n tutorial.* pt/en.

Caminho crítico

O que destrava a didática não é o visual do spotlight, mas a avaliação por snapshot com 8 expectedActions: o tutorial só avança quando a ação esperada acontece de verdade. O first-run latch síncrono StrictMode-safe garante que o latch (que marca a 1ª execução) seja montado sem dupla-invocação de efeito do React StrictMode — sem isso, o tutorial poderia tocar duas vezes ou ser marcado como visto antes de rodar.

W17 · Matemática em KaTeX

KaTeX é a biblioteca que desenha fórmulas LaTeX no navegador (ex.: \frac{a}{b}); remark-math/rehype-katex são plugins de processamento de markdown que ligam o LaTeX escrito no texto ao render do KaTeX. O CSS vem junto no bundle. Teste E2E valida o render de .katex ao vivo.

W18 · E2E real validando a didática

Além do E2E mock determinístico (sem GPU/LLM), a rodada 4 trouxe a suíte real: aula de verdade, resposta certa/errada e busca Brave, com as suas chaves vindas do ambiente — chaves nunca versionadas.

Resultados

  • E2E real npm run test:e2e:real: 3 passed (~8 min)
  • E2E mock sem chaves: 15 passed + 3 specs real-* skipped
  • Unit: 720 pass / 0 fail

Segurança e flake

  • Chaves nunca versionadas (grep limpo)
  • Helpers isolam userData em TMP e apagam; .gitignore .env.local
  • Geração real tem cauda pesada (2.5–9 min) e transientes “content vazio” → retry 1x + timeout 1.8M
  • Lock de sessão do runner (TTL 8h) pode pedir re-run

Caminho crítico

O ponto que prova a didática de verdade é o ramo resposta→juiz: certa → PASSOU + feedback; errada → NÃO PASSOU + dicas. Isso é o que diferencia “a GUI funciona” de “o tutor ensina certo”. O bug B1 ficou provado aqui: a aula real list-challenges trouxe os desafios sem o erro “requer setupRoot”.

Método de trabalho e glossário

Como o repositório foi construído, e as buzzwords definidas na primeira aparição — para quem não vive este vocabulário.

Arquitetura de entrega

  • worktree — cópia de trabalho isolada do repositório (git worktree), sem tocar no checkout principal.
  • wave (onda) — fatia paralela de trabalho dentro de uma rodada; a rodada 4 usou 4.
  • gate — checagem obrigatória (build · lint · unit · E2E) que cada onda precisa passar antes de integrar.
  • squash-merge — colapsa uma fila de commits da onda num único commit, mantendo a história limpa.
  • revisão adversarial — um revisor crítico caça defeitos no trabalho de cada onda; os commits fix1X* fecham esses achados.

Testes

  • unit — testes por função/módulo (node:test + tsx); estado puro e determinístico.
  • E2E mock — Playwright _electron controlando o app com stubs determinísticos, sem GPU/LLM/rede real; janela oculta via env.
  • E2E real — mesma suíte, mas com chaves de verdade e rede real; exige DEEPSEEK_API_KEY/BRAVE_API_KEY no shell; falha se as chaves faltam.
  • jest/playwright — ecossistema de testes JS: jest (assert/unit) e Playwright (navegação/aplicação Electron).
  • snapshot — captura instantânea do estado da UI usada para avaliar passos do tutorial.
  • expectedAction — ação que o tutorial espera ver num passo para considerar ele concluído.

Dobrado (para quem quer derivar o essencial)

E por que não houve retry no B2?

A tentação era “pega o 400 e tenta de novo”. O diagnóstico provou determinismo: o id deepseek-v4-flash-0731 sempre devolve 400, então retry só repetiria o mesmo erro e daria a sensação de progresso sem correção. A correção certa foi trocar para o id válido deepseek-v4-flash e virar o erro em algo legível (BAD_REQUEST / EMPTY_CONTENT). Retry é para falhas transitórias; causa-raiz fixa é para erro determinístico.

Por que o 400 caía no “sucesso” em código?

O parser antigo só ramificava em “erro” para um conjunto fechado de status (401/403/429/5xx). Qualquer outro código — inclusive o 400 — caía no else default, que tratava a resposta como bem-sucedida e tentava ler choices[0].message.content. Como a resposta de erro não tinha esse campo, o app produzia o erro enganoso em vez de rejeitar a chamada logo no status code.

Como o setupRoot deixou de “requerer” mas seguia preso em list-challenges?

list-challenges precisa da raiz de setup para achar os arquivos do desafio. O generateLesson criava essa raiz, mas o valor não atravessava a fronteira main⇄renderer enquanto o desafio era listado. O fix padrão do projeto — evento de progresso materializing com setupRoot/setupId → gravação em memória no main → estado compartilhado na UI via contexto — é o elo que faltava.
