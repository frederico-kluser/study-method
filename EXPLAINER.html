Resposta em uma frase

Em 3 ondas com gates verdes, o chat da aula deixou de colar respostas prontas: hoje ele digita o que o tutor diria (a ~100 tokens/segundo — token é um pedaço de texto de ~4 caracteres que a IA processa), identifica cada bolha (mensagem, resposta e review têm cor, posição, nome e avatar — o ícone circular do autor — próprios), mostra data e hora do que foi feito — inclusive a reprovação num desafio, que vira uma review (a análise da reprovação, com o código do aluno e cor própria) — e o botão “Concluir aula” só libera depois que todos os desafios da aula passaram (gating: travar uma ação até uma condição ser cumprida).

01

O pedido: 8 itens, 4 temas

O dono do app listou oito desejos para a aula. Eles se agrupam em quatro temas, e cada tema virou pelo menos uma figura neste documento.

  • 1Botão completo. “Fazer o teste” devia mostrar ícone e texto juntos (a reclamação aparecia como “[ICON] Fazer o teste”).
  • 2Gating do fim. A aula só termina quando o desafio dela é concluído.
  • 3Digitação simulada. O chat digita a resposta a ~100 tokens/segundo — nunca cola a bolha de uma vez. (Digitação simulada: o texto aparece caractere a caractere, como se o tutor digitasse.)
  • 4Identidade por bolha. IA e Pessoa identificadas com nome e avatar (imagem/ícone circular do autor).
  • 5Auto-scroll. A lista rola sozinha para manter o fim — a mensagem em digitação — visível.
  • 6Data e hora. Cada mensagem carrega data/hora; ao reabrir a aula, vê-se o que foi feito. A reprovação no desafio entra como review (análise de desafio reprovado, com o código do aluno e cor de fundo própria).
  • 7“tutor digitando” caprichado. Indicador elaborado, com animação de pontinhos.
  • 8Review e reply distintos. Review do desafio reprovado: código do aluno na mensagem + cor própria; e a resposta do tutor à pergunta como reply (resposta presa à pergunta do usuário, com cor própria e conectada a ela) — mensagem, resposta e review visualmente separáveis.

Os oito pedidos se resolvem em quatro frentes: botões (item 1), gating (item 2) e o chat em si (itens 3–8), que concentrou o grosso do trabalho nas três ondas.

02

O mistério do “[ICON]”: o botão sempre teve ícone e texto

Antes de tocar em qualquer coisa, a Onda 1 investigou: existe um literal “[ICON]” no código? A busca varreu o código-fonte, o bundle, as traduções e os stubs (simulações de serviços usadas nos testes) — nada. E os 46/46 ícones da biblioteca @mui/icons-material 9.3.1 existem. O “ícone sumido” não era um texto placeholder: era um comportamento.

O achado real: o botão usava o estado de carregamento do MUI (Material UI — a biblioteca de componentes prontos, botões e avatares, que o app usa), e o MUI v9 coloca o spinner (a animação circular de “carregando”) no centro por padrão — loadingPosition ‘center’ — escondendo o ícone e o rótulo enquanto carrega. Com loadingPosition=“start”, o spinner vai para a esquerda e ícone + texto voltam a aparecer. O mesmo hardening (endurecer: aplicar correções defensivas mesmo sem reproduzir o sintoma exato) foi aplicado ao card de proficiência “Fazer o teste”, cujo rótulo podia ser cortado.

03

A mensagem ganhou um modelo

Para dar identidade, hora e tipo a cada bolha, o chat precisou de uma estrutura de dados que representasse a mensagem — o modelo de mensagem. Sem ele, não há reply, não há review, não há hora.

A Onda 1 criou o tipo TutorChatMessage: além do papel de quem fala e do texto, cada mensagem carrega o instante em que foi criada (ts, com relógio injetável para testes) e um kind — o tipo da bolha: ‘message’ (conversa normal), ‘reply’ (resposta do tutor a uma pergunta) ou ‘review’ (erro de desafio, com errorFor apontando de qual desafio).

interface TutorChatMessage {
  role: 'user' | 'assistant';   // quem fala
  content: string;              // texto completo (markdown — formato leve com marcações)
  ts: number;                   // momento da criação → HH:MM na bolha
  kind: 'message' | 'reply' | 'review'; // o tipo da bolha
  errorFor?: string;            // review: de qual desafio é o erro
}

Duas regras nasceram junto: a regra do reply — a resposta do tutor vira ‘reply’ quando a última mensagem é do aluno e não há seção de teoria em andamento (“última ‘user’ e sem sectionId”) — e o contrato com o processo principal: o histórico enviado para fora do chat é “descascado” (stripped) de ts, kind e errorFor, porque a API externa só conhece o modelo antigo (TutorMessage[]). A LessonView ganhou um ajuste de 3 linhas para conviver com os kinds novos.

04

A identidade iMessage: quem fala, como aparece

A Onda 2 trouxe três componentes (blocos de interface com função própria) novos para src/components/chat/. O coração é o ChatBubble: nome + avatar na bolha, hora dentro dela e uma cor por kind, usando tokens de tema (cores nomeadas do tema do app: primary.main, secondary.main, error.main) — nenhum token novo foi criado. O resultado é o visual estilo iMessage — o app de mensagens da Apple, onde cada autor tem bolha, nome e hora próprios.

A reply usa secondary.main sólido, é alinhada à direita, não tem avatar e se conecta à bolha do usuário acima dela (raio superior-direito pequeno, como a segunda bolha de um fio no iMessage). A review usa color-mix (função CSS que mistura duas cores — aqui, o vermelho de erro a 10% sobre o fundo) com texto na cor primária e borda; o “Gerar novo desafio” mora dentro dela e fica desabilitado enquanto a digitação não termina. O TypingIndicator (3 pontinhos animados, com role=status — atributo que marca o elemento como região anunciável por leitores de tela) só existe no DOM — a árvore de elementos da página — enquanto algo está digitando: montagem condicional, nunca escondido por CSS.

Todo texto de interface é i18n (internacionalização: os textos do app existem por idioma, pt/en): 8 chaves novas por idioma — tutorName/youName (Tutor/Você), typingIndicator (“tutor digitando…”), dayToday/dayYesterday (Hoje/Ontem), finishBlockedTooltip e errorBubbleFilesTitle (“Código submetido”).

Contraste calibrado: por que a hora da bolha mudou de opacidade

O contraste (relação de luminosidade entre texto e fundo; ≥4,5:1 é o padrão de acessibilidade WCAG AA) foi medido por par de cor: user 4,53:1 no claro e 4,50:1 no escuro; reply 4,54:1 nos dois; error 4,50:1. Com opacidade 0,8, a hora dentro das bolhas preenchidas (user/reply) compunha 3,38–3,69:1 — reprovado. A correção: opacidade 1 nas bolhas preenchidas (o par cru passa 4,50–4,55:1) e 0,8 nas bolhas claras (message/review), onde o fundo claro dá folga enorme (8,69:1+). Um débito ficou registrado: os pares claros user/reply estão no teto do branco (4,535/4,542) — passam AA com margem mínima, e trocar os tokens ficou fora de escopo.

05

A digitação simulada: streaming que é só exibição

O contrato da Onda 1 era ~100 tokens/s; a Onda 2 o implementou no componente TypewriterText. A regra de ouro: o histórico guarda o texto completo — o streaming (entrega gradual de conteúdo em pedaços, em vez de tudo de uma vez) é apenas exibição. O componente corta o texto por typewriterCut(text, elapsedMs, tps) e avança num intervalo de typewriterDelayPerChar (≈2,5 ms por caractere → ≈400 caracteres/s).

O nó que decide tudo é a pergunta “é mensagem nova desta sessão?” — o nó âmbar acima. Ela separa quem digita de quem aparece pronto: as mensagens novas são marcadas por newMessageIndicesRef e digitam no mount (mount: quando a bolha é criada na tela); as que vêm do cache ou das mensagens semeadas (inseridas de antemão no histórico, como a discussão do erro) em remontagem nunca digitam (active=false → texto completo instantâneo). O streamingIds — a lista de mensagens em digitação — alimenta o indicador “tutor digitando…”, o auto-scroll e o gating do “Gerar novo desafio”.

O TypingIndicator entra em cena quando o turno ‘answer’ aguarda a IA ou quando alguma bolha está digitando. E o auto-scroll roda a cada passo do typewriter — onTick — e não só no fim.

Passo a passo: como o typewriter corta o texto (e por que não vaza timer)

A conta. typewriterCut assume tokens ≈ 4 caracteres: caracteres digitados = ⌊tempo decorrido × tps × 4 / 1000⌋, clampado entre 0 e o tamanho do texto. O intervalo avança a cada typewriterDelayPerChar = 1000/(tps×4) ≈ 2,5 ms por caractere. A UI só exibe text.slice(0, cut) — o conteúdo integral vive no histórico.

Cleanup. (limpeza: parar timers ao desmontar o componente) — trocar de aba desmonta a view e o intervalo morre junto; o StrictMode do desenvolvimento (modo do React que monta/desmonta componentes duas vezes para expor vazamentos) reinicia a digitação na segunda passada sem deixar o primeiro timer vivo. onStart/onDone avisam a LessonView (indicador, auto-scroll, gating do botão); onTick acompanha cada passo.

O HIGH da Onda 2 (poda de streamingIds). HIGH é a severidade de achado de revisão: um erro real que precisa ser corrigido. Abrir um pré-requisito (openPrerequisite) no meio da digitação desmonta a bolha que digitava; sem poda, o id morto ficaria no streamingIds e o indicador “tutor digitando…” viveria para sempre. A correção: um efeito poda o conjunto contra o tamanho real do histórico (history.length) — o id órfão sai, o indicador desmonta.

06

Data e hora: o tempo virou parte da mensagem

Cada bolha mostra a hora em HH:MM 24h (formato de 24 horas — 09:14, 17:03 — fixo nos dois idiomas, sem ambiguidade AM/PM) dentro da bolha, alinhada à direita. E entre mensagens de dias diferentes, um separador de dia centralizado: “Hoje”, “Ontem” ou a data completa no idioma do app.

Esses três helpers são funções puras testadas: formatChatTime (HH:MM 24h), chatDaySeparator (Hoje/Ontem/data — sempre com o ano, porque uma aula retomada do cache pode atravessar anos) e isLessonFinishBlocked (que a seção 08 usa). A hora vem do ts do modelo — e como o cache de sessão (histórico do chat guardado em memória; reabrir a aula na mesma sessão restaura o histórico sem redigitar) preserva o ts, uma mensagem restaurada mostra a hora original de criação, não a de restauração.

O e2e-lesson — e2e (end-to-end): teste que abre o app real e clica como usuário — foi reescrito para cobrir exatamente isso: a aula é reaberta pela Trilha e o chat volta do cache — mensagens completas, sem redigitar.

07

A jornada da reprovação: review → pergunta → reply

Quando um desafio de aula falha, o painel do desafio fecha e o chat da aula reabre em tela cheia com a discussão do erro. Esse fluxo — o item 8 do pedido — é a espinha dorsal da Onda 2, e a figura abaixo é o exemplo resolvido dele.

O seed — semear: inserir mensagens iniciais no histórico; aqui, a discussão do erro — acontece na montagem do chat, quando o erro do desafio está no payload (payload: os dados que acompanham uma chamada). A bolha de review é markdown determinístico (a mesma entrada sempre gera o mesmo texto — testável) montado por formatErrorBubble: título do desafio, razão parcial (N de M), o código submetido — um code block (trecho de código formatado) por arquivo, com o path como título — o checklist de testes com ✔/✖ e a saída do runner. A pergunta do tutor vem logo atrás (kind ‘message’).

A resposta do aluno — texto ou voz — viaja num turno ‘answer’ com o erro no payload, e a IA analisa a hipótese ou o erro. Como a última mensagem agora é do aluno e não há seção em andamento, a resposta do tutor vira a reply conectada. Depois do fim da digitação, o “Gerar novo desafio” habilita; passando, o gating da seção 08 libera o “Concluir aula”.

As regras do seed: dedupe sem duplicar discussão

O dedupe (impedir duplicação: não semear duas vezes o mesmo erro do mesmo desafio) tem um guard único — checagem defensiva: se já existe uma discussão ativa do mesmo desafio, não semeia de novo (protege contra StrictMode/remontagem). Três casos:

Retry do mesmo desafio após “next”: o erro anterior foi limpo, mas as bolhas ficaram na conversa. O seed remove o par antigo daquele desafio (a review com errorFor e a pergunta imediatamente seguinte) e append o par novo no fim do histórico — a cronologia natural. A discussão antiga (resposta do aluno + análise do tutor) permanece como conversa legítima.

Desafio diferente: repõe os pares de review antigos no ponto em que estavam, inserindo os novos no mesmo lugar — reposição, nunca duplicação.

Novo seed: sem pares antigos, só anexa review + pergunta no fim. O par é sempre semeado adjacente (atomicamente), e é a adjacência que distingue a pergunta semeada de uma mensagem normal do tutor.

08

O gating do “Concluir aula”

A aula só termina quando todos os desafios dela estão concluídos. A regra mora numa função pura — isLessonFinishBlocked — que lê o lastVerdict (o veredito da última tentativa do desafio: ‘passed’ = passou, ou não) de cada desafio do payload track.lesson.

O teste que trava o botão é um só: “existe desafio que ainda não passou?” (nó âmbar). Pendente (nunca tentado), reprovado, timeout ou abandonado — tudo conta como não passou. O tooltip (dica flutuante que aparece ao passar o mouse) explica: “Conclua os desafios desta aula primeiro”.

A defesa é em camadas: o botão vem desabilitado com tooltip; e o finishLesson tem um guard — checagem defensiva que impede a ação se a condição falhar — mesmo que alguém clique por outro caminho. A regra vive só no renderer — a janela/interface do app, que roda sobre o Electron (a tecnologia que constrói apps de desktop com tecnologia web); o “main” é o processo que gerencia o sistema — decisão registrada, renderer-only.

Limitação registrada: o galho “Concluir HABILITADO” não é observável em e2e — o stub do main (a simulação em memória do processo principal) não grava vereditos, e o processo principal do Electron (electron/**) ficou fora de escopo; a re-busca devolve lastVerdict nulo e a aula segue desabilitada no teste real. Os dois galhos liberados (“sem desafios” e “todos passed”) são cobertos por unit tests (testes de função isolada, sem abrir o app) de isLessonFinishBlocked.

Como a execução aconteceu: 3 ondas, gates e revisões

O trabalho foi dividido em três ondas, cada uma numa worktree própria (cópia de trabalho isolada do repositório — cada onda desenvolve na sua, sem pisar na main), executada por ~14 sub-agentes (agentes de IA especializados: implementação, revisão e checagem final).

O gate é uma checagem tripla: o build electron-vite (o empacotador que monta o app), os testes node:test (o runner de testes do Node) e o tsc --noEmit (o checador de tipos do TypeScript, rodado sem gerar arquivos) — os três ×2 (duas passadas).

Cada onda terminou com validação (sub-onda de checagem com 4 etapas — PASS nas três), passou pelo gate do snapshot de integração (snapshot: cópia verificada do código; nele rodam a checagem tripla acima) e entrou na main por squash-merge (juntar os commits da onda num único commit). O flake do e2e e a fence: o que a Onda 3 corrigiu

O teste que piscava. O indicador “tutor digitando…” é transiente: monta durante a digitação e desmonta no fim. O toBeVisible antigo polava via CDP a cada ~100 ms — e o stub digita rápido, então um poll perdido virava falha dura. A correção: waitForFunction com polling ‘raf’ (verificação repetida a cada frame de animação, ~16 ms), rodando no renderer. O predicado casa o textContent com /tutor digitando|tutor typing/i varrendo todos os [role=status] — porque o primeiro role=status do DOM é o do SessionFrame (sempre montado, sem esse texto): um querySelector simples no primeiro elemento nunca alcançaria o indicador (bug real achado e corrigido na Onda 3). O “SOME” é a negação: o unmount do indicador é a condição “typewriterIsDone”.

A fence dinâmica. A bolha de review embute o código do aluno e a saída do runner — conteúdo de autoria não controlada, que pode ecoar backticks (as cercas ``` que delimitam um code block em markdown). Com fence fixa de 3, um console.log("``") do aluno fecharia o bloco e quebraria o markdown. fenceFor(code) devolve fence = max(3, maior run de backticks + 1) — um fence de N+1 backticks nunca é fechado por uma linha de conteúdo com run ≤ N. Aplicada aos code blocks de arquivo e ao bloco de saída; o markdown gerado é validado no remark-parse real (o parser de markdown do ecossistema), e 3 testes novos cobrem o caso.

O que são worktree e squash-merge (com o exemplo desta execução)

Worktree: o git permite ter mais de uma cópia de trabalho do mesmo repositório, em branches diferentes, simultaneamente. Cada onda teve a sua — implementação, testes e revisão aconteceram isolados; nada entrou na main antes da hora.

Squash-merge: em vez de despejar dezenas de commits de trabalho na main, cada onda entrou como um único commit limpo — os 5 listados na seção 09, cada um correspondendo a uma onda (a Onda 2 entrou em dois: a implementação e o fix pós-revisão). A main fica legível: um commit = uma entrega.
