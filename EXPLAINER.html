Por que a aula trava em loading infinito no run.sh — e o que conserta

Brief original

“quando rodo uma aula pelo run.sh fica em loading infinito (MUI LinearProgress indeterminado) — descubra o porquê e resolva”

Resposta em uma frase

O loading infinito acontecia porque o StrictMode do React — ativo no modo dev que o run.sh executa — roda cada efeito de montagem duas vezes: a primeira passada consome a pendência e dispara a chamada que carrega a aula; o cleanup cancela essa chamada; e a segunda passada não tem mais pendência para disparar nada. A aula nunca chega ao estado da tela, e a barra de progresso anima para sempre. A correção guarda a pendência num retentor (holder) que sobrevive à re-execução do efeito.

02

O sintoma: barra que nunca acaba

O app é Electron + React, e o run.sh o inicia em modo desenvolvimento (npm run dev). Ao rodar uma aula — o fluxo Trilha → Aula — a tela deveria sair do roteiro e carregar a lição. Em vez disso, a interface fica no LinearProgress indeterminado do MUI: uma barra que anima sozinha, para sempre, porque o estado da tela nunca muda.

O detalhe que orienta toda a investigação: a tela não mostra erro nem vazio — fica no meio do caminho, como se o carregamento ainda estivesse em voo. O resto deste documento é a explicação de por que esse voo nunca pousa.

03

O mecanismo do bug

Quatro peças juntas produzem a trava — e nenhuma delas, sozinha, é o problema: o StrictMode no dev (efeitos em double-invoke), a pendência one-shot (apaga na leitura), a chamada IPC com timeout de 10s (cancelável) e o estado da tela (lesson · loadError). A sequência abaixo é o que acontece em cada execução do efeito de montagem da LessonView.

O passo a passo, sem diagrama:

  1. Passada 1 do setup: o efeito de montagem drena a pendência one-shot pendingTrackLesson (Trilha → Aula) e dispara loadLesson(A) — a chamada IPC com timeout de 10s.
  2. Cleanup do StrictMode: o React limpa os efeitos, e o cleanup seta cancelled = true na chamada em voo — ela passa a ser descartável.
  3. Passada 2 do setup: drainPendingTrackLesson() devolve null — a pendência já foi consumida na passada 1 — e o efeito retorna sem disparar nenhuma chamada nova.
  4. A resposta é jogada fora: a resposta do IPC, que chega em milissegundos, é descartada por if (cancelled) return — tanto no .then quanto no .catch. O próprio timeout de 10s, quando estoura, também é descartado.
  5. O estado não muda: tudo o que a tela tem é lesson = null e loadError = null — nada indica erro, nada indica conteúdo.
  6. A barra anima para sempre: sem dados nem erro, a UI não tem o que desenhar e permanece no LinearProgress indeterminado.
O ponto exato da trava está na passada 2. Cancelar a chamada, por si só, não travaria a tela — o timeout ainda poderia resolver. O que segura o carregamento é a combinação: a pendência já foi consumida, então a passada 2 não tem o que disparar; e a chamada cancelada descarta a resposta que ainda chegaria. Sinal vermelho na Figura 1: “null (já consumida)” e “resposta descartada”.
04

Por que o harness E2E não pegou

Se o bug é reprodutível no dev, por que o harness E2E não viu a trava? A resposta está em qual ambiente cada caminho executa.

Duas razões encaixadas explicam o ponto cego:

  • O harness E2E roda o build de release — modo produção, StrictMode desligado, efeitos executados uma vez só. O double-invoke não existe lá.
  • A rodada 10 (execução anterior) blindou os timeouts de IPC, mas não previu o cancelamento por re-execução de efeito — o tipo exato de problema que o StrictMode só expõe em dev.
  • O RoadmapView tem o mesmo padrão de drain, mas sem cleanup — por isso não trava: a chamada original nunca é cancelada, a resposta chega e a tela avança. Só a LessonView combinava drain com cancelamento.
05

A correção: um retentor que sobrevive ao StrictMode

A ideia é trocar a pergunta. Em vez de o efeito perguntar à pendência “tem algo para mim?” (que responde uma vez e depois null), ele pergunta a um holder — um retentor puro — que devolve o mesmo valor para cada passada do setup, porque o useRef do mesmo fiber sobrevive ao ciclo setup → cleanup → setup.

A diferença entre a Figura 1 e a Figura 2 é uma peça só. Na passada 2, o holder.get() devolve A retida no ref — em vez do null da pendência já drenada — e uma chamada nova é disparada. O restante do fluxo (cleanup, cancelamento) é idêntico; o que muda é o que a segunda passada tem para fazer.

A mudança foi mínima e cirúrgica: 3 arquivos + testes, em 1 worktree, integrados por squash em dois commits em main (be9e890 fix · 7b96b40 testes).

app/src/lib/pendingSubject.ts novo

createTrackLessonPendingHolder() — retentor puro, sem React. get() drena drainPendingTrackLesson() no primeiro acesso e retém o valor nas chamadas seguintes. Como refs e estado do mesmo fiber sobrevivem ao ciclo setup → cleanup → setup, cada passada do setup re-dispara o load com a mesma pendência.

app/src/views/LessonView/LessonView.tsx modificado

Holder em useRef com lazy init no corpo do componente; o useEffect de montagem lê holder.get(). E loadLesson estabilizado (deps [] com tIRef para tradução): a troca de idioma não re-executa mais o efeito nem recarrega aula já carregada — correção do achado HIGH da revisão adversarial.

app/tests/pendingSubject.test.ts novo

4 testes anti-StrictMode do holder + subwave de testes com 21 testes do contrato completo de pendências de trilha (pendingTrackLesson ×9, pendingTrackSlug ×6, independência/reset ×6).

</StrictMode>
LessonView · useEffect de montagem, antes do fix (esquemático) 
useEffect(() => {
  const A = drainPendingTrackLesson();  // 1ª passada: consome a pendência one-shot
  let cancelled = false;
  if (A) loadLesson(A);                  // dispara a chamada IPC (timeout 10s)
  return () => { cancelled = true; };  // cleanup: cancela a chamada em voo
}, []);

// 2ª passada: drainPendingTrackLesson() → null → o efeito retorna sem chamada nova.
// A resposta que chegar é descartada: if (cancelled) return — no .then E no .catch.
pendingSubject.ts · o holder retentor (esquemático) 
createTrackLessonPendingHolder() {
  let retained;                       // guardado no ref do mesmo fiber
  return {
    get() {
      if (retained === undefined)
        retained = drainPendingTrackLesson();  // 1º acesso: drena
      return retained;                    // passadas seguintes: retém o mesmo valor
    },
  };
}
O achado HIGH da revisão adversarial (troca de idioma)

A revisão adversarial apontou um defeito alto na primeira versão do fix: sem estabilizar o efeito, o LanguageSwitcher (seletor de idioma da interface) faria o efeito re-executar e recarregar uma aula já carregada. A correção entrega loadLesson com deps [], usando tIRef — uma referência que guarda a função de tradução — para o efeito não precisar dela na lista de dependências. Com isso, a troca de idioma não re-executa o efeito nem recarrega a aula. Após essa correção, a revisão adversarial individual deu APPROVE.

09

Fecho

Uma frase resume tudo: no dev, o efeito que carrega a aula perde a pendência entre uma execução e outra — e o retentor devolve essa pendência a cada passada, para o carregamento voltar a acontecer. O mesmo raciocínio protege a próxima vez: quando um efeito de montagem depende de um dado que “se consome na leitura”, o lugar desse dado não pode ser a pendência — precisa ser algo que sobreviva ao ciclo do StrictMode.
