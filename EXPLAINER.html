1.Resposta em uma frase

O ./run.sh do study-method (app Electron) passou a abrir e morrer em silêncio (exit 0) porque o banco SQLite era acessado por um addon nativo — o better-sqlite3 13, compilado para o NAPI 10 do Node 24 do sistema — que era incompatível com o Node 20.18 embutido no Electron 33 (NAPI 9), e carregar esse addon no runtime errado causava um segfault; a execução consertou isso em duas ondas e terminou com a solução definitiva: substituir o addon pelo SQLite embutido (node:sqlite / DatabaseSync), subir o Electron de 33.2.0 para 37.2.4, e validar com 1245 testes / 0 falhas e o app vivo por ~135s.

Tarefa original: «pesquise profundamente e arrume o projeto que além de fontes roda e quebra o run.sh», seguida da diretiva: «quero que troque o sqlite por algo que funcione e quero que só pare quando terminar».

3.O problema: o app morre em silêncio

O sintoma era assustador justamente porque não parecia um erro:

  • ./run.sh buildava e abria o Electron normalmente;
  • o processo morria em silêncio, com exit code 0 (código de saída de sucesso) — como se o app tivesse fechado sozinho;
  • ~40s depois de abrir no Linux (Acer) e em <1s no macOS (reproduzido);
  • o log não tinha nenhum erro: só warnings de fontconfig/GTK (avisos de fontes e de toolkit gráfico, inofensivos).

Sem stack trace, sem mensagem, sem exceção: um processo que "some". Para um usuário, parece bug aleatório; para o orquestrador, era um convite à investigação empírica.

4.A investigação: crash reports e probes

Como o app não imprimia nada, a pista veio de fora do app: os relatórios de crash do sistema operacional e probes (testes isolados e mínimos) que reproduziam o problema em ambiente controlado.

Ver a investigação completa (evidências)
  • Crash reports do macOS (Electron-*.ips — relatórios nativos de crash do sistema): SIGSEGV na thread CrBrowserMain dentro de node_module_register → napi_register_module_v1; a imagem binária apontada era darwin-arm64.node — ou seja, o crash acontecia ao registrar um addon nativo no processo principal do Electron (não num utility process — processo auxiliar do Electron, como rede/GPU/utilidades, que roda código nativo fora do processo principal — e não no renderer).
  • Probe isolado 1: require('better-sqlite3') dentro do Electron 33.2.0 → SIGSEGV. No Node 24 do sistema → OK. Mesmo código, dois destinos: um morre, outro não.
  • Provas numéricas (via ELECTRON_RUN_AS_NODE — variável que faz o binário do Electron rodar como Node puro): Electron 33 → Node 20.18.0, napi 9, process.versions.modules=130; Node do sistema → napi 10, modules 137.
  • Teste extra: o better-sqlite3 v13 compilado manualmente contra os headers do Electron também crashava — provando que o problema não era "prebuild velho", e sim a versão do NAPI do próprio addon.
  • Contraste útil: as versões v11/v12 (que usam o ABI V8 clássico, em vez de NAPI) funcionavam quando compiladas para o ABI do Electron — isso abriu o caminho da onda 1 (validado: alias v12.11.1 → probe OK, rows=3).

5.A causa raiz: o addon nativo com o ABI errado

Para entender, três conceitos em sequência (cada um definido na primeira ocorrência):

  1. Addon nativo — um pedaço de código escrito em C/C++ e compilado para uma biblioteca binária (.node) que o Node carrega via require() para ganhar velocidade ou acessar o sistema (é assim que o SQLite roda no better-sqlite3). É diferente de um pacote JavaScript puro: ele é máquina, não texto.
  2. ABI (Application Binary Interface) — o "contrato binário" entre o addon compilado e o runtime que o carrega: layout das funções, convenções de chamada, estruturas de memória. Se os dois lados não concordam, o comportamento é indefinido — em geral, crash. O Node expõe um número identificador do ABI em process.versions.modules (ex.: 130 no Node 20.18, 137 no Node 24).
  3. NAPI (Node-API) — uma camada de compatibilidade estável que o Node oferece para addons, com versões numeradas (NAPI 9, NAPI 10, …). A ideia é: um addon compilado contra a NAPI X deveria rodar em qualquer runtime que implemente a NAPI X. O detalhe fatal: o runtime precisa implementar a versão usada pelo addon — um addon NAPI 10 não roda num runtime que só tem NAPI 9.

Agora a montagem do problema, peça por peça:

  • O Electron 33.2.0 embute um Node 20.18 (process.versions.modules=130, NAPI 9);
  • o better-sqlite3 13.0.3 hardcoda (fixa no código-fonte do build) NAPI_VERSION=10 no binding.gyp — ou seja, todo binário dele é NAPI 10;
  • o npm ci instala o prebuild (binário .node já compilado, baixado pronto em vez de ser compilado na sua máquina) — e esse prebuild é o do Node do SISTEMA (v24: modules 137, NAPI 10), porque o npm não sabe nada sobre o Node embutido no Electron;
  • carregar esse addon NAPI 10 dentro do Electron (runtime NAPI 9) → SIGSEGV na thread CrBrowserMain, dentro de node_module_register → napi_register_module_v1.

E o motivo de ser tão silencioso: segfault (segmentation fault / SIGSEGV) é uma falha de memória no nível do sistema — o processo tenta acessar memória inválida e o sistema o mata na hora. Não é uma exceção JavaScript; nenhum try/catch consegue capturá-lo. Por isso "não tinha erro no log": o log nunca teve chance de escrever.

A frase que resume tudo: o addon certo (que funciona no Node 24) no runtime errado (Node 20.18 do Electron) segfaulta; e o addon recompilado contra o Electron também segfaulta, porque o runtime NAPI 9 simplesmente não implementa a NAPI 10. Não havia "prebuild mágico" do v13 que salvasse.

6.Mergulho técnico (opcional)

Ver o detalhamento da cadeia NAPI (para quem quer o "porquê" fino)
  • binding.gyp é o arquivo de build do addon. No better-sqlite3 13.0.3, a linha NAPI_VERSION=10 está hardcoded — o binário declara "eu quero a NAPI 10".
  • O prebuild é baixado pelo npm porque o pacote publica binários prontos por plataforma/arquitetura (ex.: darwin-arm64.node). O npm ci instala o prebuild do Node do sistema — o npm não sabe que o destino real é o Node embutido do Electron.
  • Ao carregar, o runtime chama a função de registro do addon: node_module_register → napi_register_module_v1. É aí que o runtime NAPI 9 encontra chamadas NAPI 10 e a memória estoura → SIGSEGV.
  • O teste empírico decisivo: compilar o v13 contra os headers do Electron (eliminando a "culpa" do prebuild) também crashava. Isso prova que a incompatibilidade é de versão da NAPI (10 não existe no runtime 9), não de binário velho.
  • Por que v11/v12 funcionavam compilados para o Electron? Porque usam o ABI V8 clássico (não NAPI): com node-gyp --target=<versão-do-electron> o binário é gerado exatamente para o ABI do runtime — a base da onda 1.

7.A solução, em duas ondas

O orquestrador trabalha em ondas (grupos de trabalho paralelos em worktrees isoladas, integrados com gate). Aqui foram duas ondas — a segunda só existiu porque o usuário, vendo a primeira funcionar, pediu algo melhor:

Onda 1 (tentativa): contornar o ABI com um alias compilado onda 1

A primeira resposta ao crash foi fazer o addon certo para o Electron, sem trocar de biblioteca:

  • Alias npm (instalar um pacote sob outro nome): better-sqlite3-electron = npm:better-sqlite3@12.11.1 — a v12 usa ABI V8 clássico e funciona quando compilada para o ABI do Electron (validado: probe OK, rows=3).
  • tools/ensure-native-abi.sh: compila o alias para o ABI do Electron com node-gyp --target=<electron> --dist-url=https://electronjs.org/headers, npm_config_force_build=1, com marker idempotente (segunda execução é instantânea).
  • Loader lazy no connection.ts: escolhe o pacote pelo runtime (!!process.versions.electron) e faz require só na hora do uso — sem import estático, para nunca carregar addon no runtime errado.
  • Hooks postinstall/predev/pretest:e2e: o script roda sozinho (self-healing) após instalações.

Veredito da onda 1: funcionou — o app abria e permanecia vivo. Mas exigia toolchain de build nativo (Xcode Command Line Tools no macOS / build-essential + python3 no Linux) e rede para baixar os headers do Electron; sem isso, a instalação falhava. Era uma solução frágil: dependia de compilação pós-install — exatamente o tipo de coisa que quebra em outra máquina.

Onda 2 (solução final): node:sqlite + Electron 37.2.4 onda 2 · final

O usuário então deu a diretiva: «quero que troque o sqlite por algo que funcione e quero que só pare quando terminar». A onda 2 substituiu a convergência da onda 1 pela solução definitiva:

  • node:sqlite (DatabaseSync) — o SQLite embutido no próprio Node (disponível desde o Node 22.5, sem flag desde 22.13) e, portanto, também no Electron. Zero addon nativo, zero compilação pós-install, zero ABI a casar — a classe inteira do problema deixa de existir.
  • Electron 33.2.0 → 37.2.4, que embute Node 22.17.1 — já com node:sqlite unflagged (sem precisar de flag experimental).
  • Removidos: o alias, o ensure-native-abi.sh, os hooks e o loader — o código volta a ser simples.
  • e2e determinístico: o launch passa --lang=pt-BR (switch do Chromium) — as specs assumem a UI em pt-BR, então o locale do host não pode mais afetar o veredito; 2 specs foram alinhadas ao produto real ("Gerar nova aula" é o botão de verdade, e a aula exibida é a curta — o markdown completo renderiza corretamente e é coberto por testes unitários).

O código que passou a abrir o banco (de app/electron/main/db/connection.ts):

import { DatabaseSync } from 'node:sqlite';

export async function openSqlite(dbPath: string) {
  await fsp.mkdir(dirname(dbPath), { recursive: true });
  const db = new DatabaseSync(dbPath);         // banco de arquivo
  db.exec('PRAGMA foreign_keys = ON');         // FKs de fato enforced
  const migrator = createMigrator(db);
  let closed = false;
  return {
    db,
    migrate: migrator,
    close() { if (closed) return; closed = true; db.close(); }, // idempotente
  };
}

Notas: o PRAGMA foreign_keys (configuração de chave estrangeira do SQLite) passou a ser aplicado via exec, e o close() é idempotente (fechar duas vezes não quebra).

E as transações, em app/electron/main/db/repo.ts — o DatabaseSync não tem o helper db.transaction(fn) do better-sqlite3, então o equivalente é explícito:

function withTransaction<T>(db: DatabaseSync, fn: () => T): T {
  db.exec('BEGIN');
  try {
    const result = fn();
    db.exec('COMMIT');
    return result;
  } catch (err) {
    db.exec('ROLLBACK');
    throw err;
  }
}

8.O que mais foi consertado no caminho

Durante a execução, o orquestrador encontrou e corrigiu outros três problemas que se misturavam ao crash (mais um requisito levantado pela solução):

  • t.sh portável bash 3.2/5 — o runner de testes usava globstar (**, recurso do bash 5) para coletar os testes recursivamente; no macOS o bash é 3.2, o globstar não existe e o npm test rodava só 14 de 90 arquivos. A coleta do caso diretório passou a usar find + sort (portável), mantendo a empty-glob guard (o runner falha se nenhum teste casar — nunca verde silencioso):
while IFS= read -r f; do files+=("$f"); done < <(
  find "$target" -type f \( -name '*.test.ts' -o -name '*.test.tsx' \) | sort
)
  • Teste i18n-wiring robusto ao navigator sintético do Node 21+ — no Node 24, o navigator.language sintético vira 'en-US' e quebrava o default pt-BR do app; o teste passou a neutralizar o navigator (defineProperty com value: undefined + restore no after()) — a produção só ganhou comentários.
  • e2e determinístico — --lang=pt-BR no launch do Electron (mais LANG como fallback no harness real): o locale do host não pode mais mudar o idioma da UI e, com isso, o veredito das specs.
  • Floor de Node ≥ 22.13 — como o node:sqlite só é unflagged desde 22.13, o requisito mínimo de Node subiu para >=22.13 no install.sh, READMEs e no campo engines do package.json.

11.Decisões autônomas

Decisões tomadas pelo orquestrador sem consultar o usuário (além da diretriz geral), registradas nos fatos:

  • Onda 2 por diretiva: a troca do sqlite veio de ordem do usuário; a escolha de como — node:sqlite + Electron 37 — foi autônoma, por serem nativos/embutidos: sem addon, sem ABI, sem toolchain de build (a fragilidade exata da onda 1).
  • e2e: determinismo no harness, não nas specs: o fix de locale foi no launcher (--lang=pt-BR), em vez de reescrever as specs em inglês — preserva o produto (UI pt-BR) e torna o veredito independente do host.
  • Tolerância a falha de persistência: se o sqlite falhar ao abrir, o app sobe mesmo assim, sem persistência (try/catch no index.ts → repo undefined e canais de persistência desativados) — degradacão graciosa, nunca crash.
