Run 3 — Premissa pedagógica

Data: 2026-08-28 Branch: main Trilha auditada: nodejs-do-zero (136 desafios)

Esta página resume a terceira execução do deep-orchestrator no projeto study-method (app Electron de estudo de programação — renderer React/MUI v9 + electron-vite): o que você pediu, o que foi entregue em 3 ondas, como a premissa pedagógica foi auditada nos 136 desafios existentes e como o sistema passa a garanti-la daqui pra frente.

2 · O que você pediu

O pedido central foi estabelecer uma premissa pedagógica para a trilha nodejs-do-zero: nenhum desafio pode cobrar conhecimento que ainda não foi ensinado. Em volta dela, sete pedidos operacionais de navegação, limpeza e performance. Clique em cada item para ver o detalhe.

1 Premissa pedagógica clara
Os desafios da trilha só podem exigir o que já foi ensinado nas aulas anteriores. Exemplo de violação citado por você: um teste que usa assert.throws para cobrar validação de erro quando o aluno ainda não aprendeu nem typeof nem throw.
2 Critérios de entrada
A trilha tem critérios de entrada (uma trilha de senso iniciante deve ter nenhum pré-requisito). Cada aula tem como critério de entrada o conceito da aula anterior. O prompt de geração de aula deve incluir os critérios + as aulas anteriores, e nunca exigir nada não ensinado.
3 Validação com os textos das aulas anteriores
Para validar um desafio, o sistema deve pegar todos os textos das aulas anteriores + os critérios da aula e verificar principalmente se os testes são satisfazíveis com o conhecimento ensinado.
4 Thinking máximo na criação
Criação de testes e de todo o conteúdo com o raciocínio máximo possível da LLM (thinking máximo no prompt).
5 Histórico de navegação com voltar
Manter histórico de navegação na trilha com botão Voltar — hoje o contexto se perde ao ir para Settings e voltar.
6 Botão limpar dados de avanço
Um botão para limpar todos os dados de avanço do estudo (progresso, desafios resolvidos etc.).
7 Última aula na tab Aula, sem botão voltar
Na tab Aula: abrir a última aula aberta (ou nenhuma, se não houver), e não mostrar botão Voltar nessa tab.
8 Velocidade de 10 tokens/segundo nas reviews
As respostas de IA online (reviews de desafios) devem ser escritas a 10 tokens por segundo — uma digitação lenta e didática. Respostas processadas por IA (não escritas) continuam livres/instantâneas.

Onda 2

Autoria — prompts pedagógicos + validação semântica pós-execução

Esta onda fez a geração de conteúdo (novos desafios, regeração, correção) respeitar a premissa — e criou a CLI de auditoria para você verificar qualquer desafio a qualquer momento.

  • Prompt de regeração (buildRegenerationPrompt) — injeta os CRITÉRIOS DE ENTRADA da aula (ou a marca "(nenhum — trilha de senso iniciante)"), o CONTEÚDO DAS AULAS ANTERIORES, a regra "NUNCA cobrar algo não ensinado" e a instrução de raciocínio "PENSE PROFUNDAMENTE, PASSO A PASSO" (thinking máximo).
  • Formato condicionado a tratamento de erro — a heurística contextTeasesErrorHandling (padrões throw | typeof | try | catch | assert.throws | exceção | validação no contexto) decide se o formato do desafio pode incluir caso de erro.
  • Loop semântico pós-execução — o desafio gerado passa por verifyChallengeAgainstContext: reprovou → retry com o motivo da reprovação (lastReason, limite MAX_SEMANTIC_ATTEMPTS = 2); aprovou → entrega; contexto indisponível (UNAVAILABLE/INVALID_JSON/sem contexto) → entrega por execução; 2 reprovações → INVALID_CODE.
  • CLI track:challenge:context — <slug> <module> <lesson> <challenge>, usa DEEPSEEK_API_KEY; exit 0 = aprovado, exit 1 = reprovado ou não verificado; multi-arquivo concatena files[].solutionCode; sem chave → erro claro + exit 1. E track:new --criteria "a; b; c" para declarar critérios de entrada ao criar.
  • Robustez e revisão — handler monta contexto com try/catch defensivo + console.warn; fixes do revisor: log no fallback e erro limpo no CLI. 15 testes novos.

5 · Como a premissa é garantida daqui pra frente

Além de consertar o conteúdo existente, o sistema agora verifica e gera com a premissa embutida — não depende mais do bom humor da LLM:

Validação semântica pós-geração, com veredito por teste

Todo desafio gerado/regenerado passa por verifyChallengeAgainstContext, que confronta cada teste com os textos das aulas anteriores (aula atual excluída, com teoria completa; anteriores truncadas a 1500 chars). O veredito é por teste: um único teste exigindo algo não ensinado reprova o desafio.

Retry com feedback (loop semântico)

Reprovação → nova tentativa com o motivo da reprovação (lastReason) no prompt, até MAX_SEMANTIC_ATTEMPTS = 2. Aprovado → entrega. Contexto indisponível (CONTEXT_UNAVAILABLE/INVALID_JSON) → entrega por execução (não bloqueia o fluxo sem motivo). 2 reprovações → INVALID_CODE.

CLI de auditoria track:challenge:context

Você pode auditar qualquer desafio existente a qualquer momento, sem mexer no app:

npm run track -- track:challenge:context nodejs-do-zero <module> <lesson> <challenge>

Exit 0 = aprovado; exit 1 = reprovado ou não verificado (incluindo chave ausente). Desafios multi-arquivo são auditados com files[].solutionCode concatenado.

Geração já nasce com a premissa

O prompt de regeração carrega os critérios de entrada (ou a marca "(nenhum — trilha de senso iniciante)"), o conteúdo das aulas anteriores e as regras "NUNCA cobrar algo não ensinado" + "PENSE PROFUNDAMENTE, PASSO A PASSO" (thinking máximo). Trilhas novas declaram critérios com track:new --criteria "a; b; c" e o formato do desafio (com/sem caso de erro) é decidido pela heurística contextTeasesErrorHandling.

7 · Nota de ambiente — falta a DEEPSEEK_API_KEY

Bloqueio de ambiente registrado

A variável DEEPSEEK_API_KEY não existe nesta máquina — foi procurada no ambiente (env, shells), no keychain e no store do app. Sem a chave:

  • A CLI track:challenge:context retorna erro claro + exit 1 (não falha silenciosamente);
  • A re-verificação runtime dos desafios via CLI fica pendente — a auditoria da onda 3 foi feita com o julgamento do agente (LLM em thinking máximo) sobre os textos reais, mas a confirmação automatizada pela CLI depende de você configurar a chave.
Como configurar (pós-condição documentada)

Opção A — copiar o exemplo e preencher:

cp .env.local.example .env.local
# edite .env.local e preencha: DEEPSEEK_API_KEY=sk-...

Opção B — exportar no shell:

export DEEPSEEK_API_KEY=sk-...

Depois, re-verificar qualquer desafio com:

npm run track -- track:challenge:context nodejs-do-zero <module> <lesson> <challenge>

Exit 0 = aprovado contra o contexto pedagógico; exit 1 = reprovado ou não verificado.
