01O cenário: um app em três camadas, uma só mexida

O study-method é um app de estudo desktop feito com Electron + React. Um app Electron é dividido em três camadas que só funcionam juntas:

  • processo main (o backend do app: teclado, voz, busca, IA local) — é onde roda o trabalho pesado;
  • preload (camada fina que entrega dados do main ao renderer com segurança) — a ponte;
  • renderer (a janela com a UI React) — o que aparece na tela.

Esta execução mexeu em um único lugar: o processo main. Preload e renderer ficaram intactos.

Aprofundar: por que um app desktop tem três camadas?

Pense num restaurante: a cozinha é o processo main (prepara tudo: banco de dados, arquivos, serviços do sistema), o salão é o renderer (a UI que a pessoa vê) e o garçom é o preload (leva o pedido do salão à cozinha e traz o prato de volta — sem deixar o cliente entrar na cozinha). Essa separação existe por segurança: o renderer é o que recebe conteúdo de fora, e o preload controla o que ele consegue pedir.

02Sintoma 1: o dev server morria no primeiro import

O run.sh começa subindo o dev server — o vite (o dev server e o empacotador do frontend). Ao iniciar, o vite precisa resolver os imports — as declarações que trazem um módulo de outro arquivo para o código — de duas dependências: @fontsource/chakra-petch/400.css e motion/react. O package.json as declara desde o commit f5f2c7f, mas o node_modules deste checkout não as tinha: ninguém tinha rodado a instalação.

O ponto exato da quebra: o nó vermelho da figura — o node_modules desatualizado. O dev server não instala nada sozinho: ele só procura, não acha e aborta com o erro fatal Failed to resolve import.
Aprofundar: o que o npm ci fez de diferente?

O npm ci é a instalação determinística: em vez de resolver versões de novo, ele instala exatamente o que o package-lock.json — o lockfile, o registro com as versões exatas — manda. Ele rodou com HUSKY=0 (a variável que desliga os hooks de git — os ganchos que rodam sozinhos durante comandos — durante a instalação) e instalou o lockfile completo: motion e @fontsource/chakra-petch agora existem de verdade no node_modules.

Bônus de ambiente: esse mesmo npm ci rodado no app conserta o ambiente do usuário — o marcador obsoleto .install-ok some e o run.sh se auto-repara na primeira execução depois do merge.

03Sintoma 2: sete avisos no build

O outro problema era mais sutil. O build do main é feito pelo rollup (o empacotador que o vite usa no build de produção), e ele passou a emitir 7 avisos: X is dynamically imported by A but also statically imported by B — dynamic import will not move module into another chunk.

Aviso não é erro — o build passava — mas sinalizava código com os dois estilos misturados e poluía a saída do build. Para entender: o empacotador corta o código em chunks (os arquivos finais que o app carrega), e a regra do jogo é ele saber onde cada módulo fica no momento do build. Um import dinâmico (o import() chamado dentro de uma função, que carrega o módulo só quando aquela linha executa) embaralha esse cálculo quando o mesmo módulo também chega por import estático (declarado no topo do arquivo) em outro lugar.

O conserto da ONDA 1: trocar os 22 sites de import() por import estático no topo, em 8 arquivos do main, envolvendo 7 módulos (settingsStore, trackLoader, trackService, tutorChat, challengeExec, modelStore e EmbeddedLlmService — o serviço do modelo de IA que roda dentro do app). No total, +12/−23 linhas.

O que importa ver nesta figura é a seta tracejada: ela é o conserto — a troca de import() por import estático no topo. É ela que faz o rollup decidir o chunk no build e zera os avisos.
Aprofundar: import dinâmico vs estático — exemplo resolvido

Exemplo de sintaxe (ilustrativo — não é o código real do repositório):

// ANTES — import() dinâmico: o módulo só é buscado quando a função roda
async function falar(texto) {
  const tts = await import('./localTts.js');
  tts.falar(texto);
}

// DEPOIS — import estático no topo: o empacotador resolve no build
import * as tts from './localTts.js';

async function falar(texto) {
  tts.falar(texto);
}

Exemplo de sintaxe ilustrativo — não é o código real do repositório.

Por que o aviso importa: com o import() no meio, o rollup via o módulo chegar por dois caminhos e avisava que não moveria o módulo para outro chunk. Não era erro, mas era imprevisibilidade: o lugar de cada módulo no bundle final (o conjunto de arquivos que o app carrega) só ficava claro de forma ambígua — e o build gritava isso 7 vezes.

04A subwave de teste: 25 testes novos

Mudar imports e mexer em serviços não se entrega no grito: veio uma subwave (uma onda dedicada só a escrever testes) com 25 testes novos em dois arquivos:

  • tests/embeddedLlmService.test.ts (17 testes): o roteamento proxy↔in-process (proxy = chamada para um servidor externo; in-process = para o processo interno), o activeId (qual modelo está ativo em cada momento), o erro LOCAL_MODEL_NOT_INSTALLED (modelo local não instalado), os deltas (pedaços de resposta que chegam aos poucos), o guard de dispose (impede usar o modelo depois de liberar seus recursos), as options do chat asseeradas e o escape hatch (porta de fuga: uma variável de ambiente que força outro caminho) STUDY_METHOD_LLM_IN_PROCESS.
  • tests/e2eStubs.test.ts (8 testes): o gate de segurança no-op (operação que não faz nada) fora de E2E, o registro exato de 66 canais, 4 cenários de e2eGatePhase (a fase do ciclo em que o app é operado de fora, de ponta a ponta), um smoke real de trilha (teste que percorre o caminho principal para ver se nada quebrou) e o workspace E2E isolado.

Sobre os termos: E2E (end-to-end) é testar o app inteiro operado como um usuário real; os e2eStubs (os stubs — peças falsas que imitam uma dependência real para o teste isolar o resto — do modo E2E) são o módulo que registra os canais de teste. O trabalho passou ainda por um revisor adversarial (revisão que tenta ativamente achar defeitos no que foi feito): ele apontou WARNING e os 5 achados foram corrigidos antes do gate — que fechou com npm ci + lint (checagem automática de estilo e erros comuns) + tsc (o verificador de tipos do TypeScript) ×2 + 1937 testes + build, tudo verde.

O que importa nesta figura: os 25 testes novos alimentam o gate — e o gate é o guardião que só libera a entrega com 1935 testes passando, 2 skipped pré-existentes e build sem avisos.

05Verificações, decisões e limites

O gate fechou verde no snapshot de integração: npm ci + lint (tsc ×2) + 1937 testes (1935 pass, 2 skipped pré-existentes) + build de main/preload/renderer. Os avisos do build do main caíram para 0, e o renderer resolve motion/react e @fontsource/chakra-petch — 24 assets (arquivos estáticos, como fontes, que o build copia) de chakra-petch .woff2 no bundle. A validação no estado integrado (val-onda1-gate) passou com zero avisos, e as duas revisões — a adversarial pré-merge e a do diff integrado — deram APPROVE, sem nada a refutar.

Decisões autônomas registradas:

  • Ruído de sistema fora de escopo (não é problema do repositório): o aviso Gtk appmenu-gtk-module, os avisos de fontconfig (48-guessfamily.conf) e o ExperimentalWarning de SQLite do Electron.
  • O npm ci em app/ conserta o ambiente do usuário: o marcador .install-ok obsoleto some e o run.sh se auto-repara na primeira execução pós-merge.
  • Premissa de ambiente: o projeto real vive em app/ (a raiz do repositório tem só um package-lock.json placeholder de 91 bytes) — todo npm ci/gate roda com cwd em app/.

Limites declarados (fora de escopo):

  • e2eGatePhase: o export de produção sem chamador (dead export — função exportada que nenhum código chama) é pré-existente; foi registrado, não mexido — decisão de produção.
  • E2E Playwright (specs): não rodadas nesta execução (exigem build + app); o novo smoke unitário cobre o grafo de trilha sem precisar de build.

Aprofundar: o que é um worktree e por que a onda roda isolada?

Um worktree é uma cópia isolada do repositório: a onda trabalha nela sem sujar o principal. É por isso que o gate roda numa versão integrada antes do merge — cada mudança só entra depois de provar que não quebra o todo. No fim, cada branch é integrada por squash merge: todos os commits daquela branch viram um único commit no histórico.

Aprofundar: o e2eGatePhase que ficou de fora

O e2eGatePhase — a fase do ciclo em que o app é operado de fora — tem um export de produção sem chamador (um dead export: função exportada que nenhum código chama). Ele é pré-existente e não tem relação com esta execução: foi registrado como fora de escopo, por decisão de produção. O que a subwave fez foi testá-lo: os 8 testes do e2eStubs cobrem seus 4 cenários.
