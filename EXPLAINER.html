Limpa de relatorios — o que ficou e o que saiu (worktree relatory)

A tarefa original

"fazendo uma LIMPA em markdowns e documentos que temos de relatório, só quero o que for relevante ao final, não faça merge na branch principal, delete as sub-worktrees e fique apenas com a worktree relatory"

Resposta em uma frase

A execução classificou os 72 arquivos de docs/ em três vereditos — relato de processo (remover), documentação viva (manter) e conteúdo durável (consolidar antes de remover) —, migrou o durável para os docs vivos e removeu 11 arquivos (~2.300 linhas): 10 relatórios de rodada + um EXPLAINER.html. Resultado: 5 squash commits no branch do/wt/relatory, 26 arquivos tocados, saldo +198 / −2435 linhas, gates validate 77/77 e spec-conformance 11/11 verdes, com a branch principal intocada e a worktree relatory persistindo.

Leitor declarado

Portão de complexidade

Alta interatividade — muitas peças só fazem sentido juntas (ondas, vereditos, commits, gates). Por isso: figuras com legenda-afirmação, arestas rotuladas e sinalização do caminho crítico.

01

O ponto de partida: 72 arquivos em docs/

Antes da limpa, o repositório acumulava 72 arquivos em docs/ (o diretório de documentação do projeto). Três naturezas de documento se misturavam ali:

  • Relatórios de rodada — documentos que registram o processo de uma rodada de execução (ondas, commits, gates). São relato de processo: úteis na hora, sem valor depois.
  • Documentação viva — documentos que continuam servindo como fonte de verdade do projeto: specs implementadas, guias, a fonte da logo.
  • Conteúdo durável — conhecimento técnico que vale além da execução que o produziu, mas estava preso dentro de relatórios que deveriam sair.

A tarefa pedia: manter só o que fosse relevante, sem merge na branch principal (a branch main — a linha de desenvolvimento "oficial" do repositório), deletar as sub-worktrees e ficar apenas com a worktree relatory (cópia de trabalho do repositório num diretório próprio, presa à branch do/wt/relatory; é ela que permite mexer no projeto sem tocar em main).

O que é um "pin" e por que ele é atualizado (novato)

Alguns documentos registram o estado exato de uma parte do sistema — no caso, a engine de trilha. Esse registro (o pin) usa números de bateria: 841/96 antes, 717/112/249/92 com bateria A13–A16 depois. Atualizar o pin é dizer "o documento agora descreve o estado atual da engine", e o protocolo de bump (§5.1) é o procedimento registrado para fazer isso de forma padronizada.

Fonte dos fatos: "pin da engine atualizado em 16-engine-de-trilha.md (841/96 → 717/112/249/92 com bateria A13–A16)" + "protocolo de bump em 16-engine-de-trilha.md §5.1".

Por que consolidar ANTES de remover (exemplo com R8/R10)

Os relatórios relatorio-rodada8, relatorio-rodada10, relatorio-rodada10-diag e relatorio-rodada12 (R8/R10/R10-diag/R12) carregavam conteúdo durável — conhecimento que vale além daquela rodada. Se fossem simplesmente apagados, esse conhecimento sumiria junto. A ordem certa é: 1) extrair o durável e salvá-lo num doc vivo; 2) só então remover o relatório. É isso que as ondas 2 e 3 fazem, nessa ordem.

O que é "rename 100%"? (novato)

Quando o git compara dois commits e encontra um arquivo que saiu de um caminho e entrou em outro sem nenhuma mudança de conteúdo, ele reporta um rename com similaridade 100%. No commit 2a98edd, o dossiê de linguagens só mudou de endereço: docs/linguagens/README.md → docs/research/08-multilingua-trava-deterministica.md. Histórico preservado, conteúdo intocado.

O que significa "G-10 sumiu"? (novato)

Um gate (ou checagem) pode existir porque um arquivo o provoca. O gate G-10 era disparado pelo relatorio-rodada12. Quando a limpa removeu esse arquivo, o problema que G-10 detectava deixou de existir — e o próprio gate deixou de aparecer na contagem. Por isso o validate fechou 77/77: com G-10 fora, todas as 77 checagens restantes passaram.

Fonte dos fatos: "validate 77/77 VERDE (G-10 sumiu com a remoção do relatorio-rodada12)".

O que é uma git worktree, passo a passo (novato)

Normalmente você tem uma pasta do repositório com uma branch de cada vez. Uma git worktree cria uma segunda pasta para o mesmo repositório, presa a uma branch diferente — sem conflitar com a primeira.

  1. O usuário pede uma limpa, mas proíbe tocar na branch principal e pede para manter só a worktree relatory.
  2. A execução trabalha 100% na branch do/wt/relatory, dentro da worktree relatory.
  3. Para cada onda de trabalho paralelo, a execução cria worktrees-filhas temporárias — e as remove ao fim de cada onda (foram 8 no total).
  4. Os 5 squash commits ficam só em do/wt/relatory; main nunca recebe merge.
  5. No fim, a worktree relatory permanece, como pedido.

Fonte dos fatos: "MODE=contido · trabalho 100% em do/wt/relatory · 8 worktrees-filhas criadas e removidas · checkout principal nunca tocado" e "Worktree relatory permanece (persistente, como pedido pelo usuário)".
