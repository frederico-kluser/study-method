Tutor study-method · Persistência SQL das aulas

O tutor (Electron + React/MUI v9) deixou de gerar aulas longas e descartáveis: agora toda aula é persistida em um banco SQL interno, curta, encadeada e com árvore de progressão.

Em uma frase: esta entrega colocou um banco SQL interno no tutor, fundiu os desafios dentro da aula, criou aulas de 1–2 parágrafos com resposta → próxima aula do mesmo assunto, e construiu uma árvore de evolução com hints que quebram a aula em sub-aulas — tudo coberto por 1200 testes unitários verdes.
Quem é o leitor deste documento

Dois perfis: o novato na codebase (que precisa entender o que foi feito e como as camadas se encaixam) e o mantenedor (que precisa voltar ao código sem se perder).

Para o novato, os termos técnicos aparecem explicados na tabela de definições. Para o mantenedor, cada segmento nomeia os arquivos e funções reais do repositório.

Todo fato vem do arquivo de fatos da execução (.deep-orchestrator/.../fatos.md). Nada aqui é inventado.

1. O problema

O tutor não persistia nada. Gerava aulas longas que se perdiam, os desafios ficavam separados da aula e não havia noção de progressão por assunto. O pedido consolidado:

  1. Salvar toda aula num banco de dados SQL interno.
  2. Fundir os desafios dentro da aula (não em uma view separada).
  3. Seleção por assunto com um botão “Continuar” por aula, mostrando quantas aulas já foram feitas daquele assunto.
  4. Botão “Gerar aula” renomeado para “Gerar nova aula”.
  5. Aula gerada sempre de 1–2 parágrafos + um input onde o aluno escreve o que entendeu OU responde uma pergunta.
  6. Ao responder → próxima aula do mesmo assunto (progressão). Árvore de evolução visível por um botão.
  7. Algumas perguntas são os desafios fundidos → bem explicados, com hints (até 3 dicas; no 4º clique pergunta o que não entendeu e quebra a aula em mais aulas). Botão “estou perdido” com o mesmo efeito.
  8. Progresso gradual, muita prática e pouca teoria. A árvore cresce; os desafios crescem em complexidade conforme o aluno evolui.
  9. Testes unitários para tudo.

2. A solução em uma frase de arquitetura

O sistema foi construído em camadas separadas — sql → domínio → ipc → preload → renderer — cada uma com responsabilidade clara e testável. A linha do tempo está mais abaixo.

3. Glossário — termos definidos onde aparecem

TermoDefinição
SQL nativoBanco acessado por um bind nativo no process main do Electron — o mesmo padrão já usado pelo node-llama-cpp (externalizado + asarUnpack).
migratorCódigo que aplica o schema de forma idempotente (CREATE TABLE IF NOT EXISTS + índices IF NOT EXISTS): pode rodar várias vezes sem quebrar.
squash-commitVários commits fundidos em um só, deixando o histórico limpo e atômico.
DI (injeção de dependência)A conexão com o banco é injetada nos módulos em vez de cada um criar a sua — deixa o código testável e desacoplado.

CRUDCreate / Read / Update / Delete — operações básicas do repositório sobre o banco.
PRAGMA foreign_keysDiretiva SQL que exige o enforcement de chaves estrangeiras em runtime no SQLite.
PURO (módulo puro)Sem dependência de Electron nem de banco — roda em qualquer runtime, é testável sem DOM.

4. O schema (7 tabelas)

Base relacional normalizada, contrato congelado para as demais camadas. As tabelas respeitam dependências de chave estrangeira na criação:

  • subjects — assuntos (disciplinas) raiz
  • lessons — aulas, markdown curto (1–2 parágrafos); árvore pai→filha via parent_lesson_id; origem via origin_lesson_id
  • lesson_answers — respostas do aluno, encadeiam para a próxima aula
  • challenges — desafio fundido dentro da aula (statement + testes + solução em JSON)
  • challenge_hints — até 3 hints por desafio (position 0–2, índice único)
  • hint_break_events — gatilho de quebra: motivo 'hint-4th' ou 'lost-manual' + o que o aluno disse
  • progress — contagem agregada por (subject, lesson), chave primária composta

Ids das tabelas de domínio são TEXT (gerados pela aplicação); challenge_hints e hint_break_events usam INTEGER AUTOINCREMENT. Versão do schema: SCHEMA_VERSION = 1.

Por que SQLite e não outro banco?

better-sqlite3 foi a escolha de SQL interno: síncrono/determinístico (fluente no main), DI-friendly e unit-testável com :memory:. Foi uma decisão autônoma registrada nos fatos.

5. A aula curta que encadeia

O motor da aula resume a matéria para 1–2 parágrafos, com um limite de ~80 palavras por parágrafo truncado com reticências (maxParagraphs=2). O aluno responde a uma pergunta ou escreve o que entendeu; ao responder, avança para a próxima aula do mesmo assunto.

6. Desafios fundidos + hints + “estou perdido”

Algumas perguntas da aula são os desafios fundidos. O aluno pode pedir até 3 dicas; no 4º clique o sistema não dá a 4ª dica: pergunta o que o aluno não entendeu e quebra a aula em mais aulas. O botão “estou perdido” tem o mesmo efeito.

Essa lógica vive no motor de hints (hintEngine.ts): o fluxo nextHint conta os hints usados (0, 1, 2, 3 = 4 cliques) e devolve {kind:'break', reason:'hint-4th'} quando estoura o máximo; o botão de perdido devolve {kind:'break', reason:'lost-manual'}. O plano de quebra (buildBreakPlan) decide como dividir, e a repo garante que a aula quebrada gere ≥2 sub-aulas ligadas por parent_lesson_id/origin_lesson_id.

Gatilho 1 — 4º hint
Depois de 3 dicas, o 4º clique dispara a quebra (hint-4th) — não existe “dica 4”.
Gatilho 2 — estou perdido
Botão manual com o mesmo efeito (lost-manual).
Registro
Cada quebra registra um hint_break_event e a árvore cresce.

7. Progressão em árvore

O motor de progresso (progressEngine.ts) calcula a dificuldade dinamicamente: progressionDifficulty parte de um baseline (padrão 1) e sobe com as respostas, até um teto (cap 5). A complexidade cresce conforme o aluno evolui — muita prática, pouca teoria.

A árvore de evolução é visível por um botão. Quando o aluno se perde, a aula “quebra” em sub-aulas que se tornam filhas — a árvore cresce e os desafios seguintes ficam mais complexos.

Como a dificuldade cresce

progressionDifficulty(answeredCount, baseline=1) devolve 1–5, com difficulty = baseline + floor(answeredCount / TARGET_ANSWERS_PER_STEP). Respostas poucas mantêm o baseline (mais gradual); depois de um limite de maestria (MASTERY_THRESHOLD = 10), a próxima aula já sobe de rampa.

8. Seleção por assunto e botão “Continuar”

O IPC de persistência expõe ao renderer: listTopics, listLessonsBySubject, getLessonById, recordAnswer e markLessonCompleted. A preload expõe essa API de forma segura ao React/MUI v9.

Na seleção de aulas, cada assunto mostra um botão “Continuar” com a contagem de aulas feitas (answeredCount) — o rótulo fica “Continuar · N aulas feitas”. Quando não há aula pendente, o botão primário vira “Gerar nova aula”.

10. A prova — 1200 testes e o gate

O gate completo (build + lint + 1200 testes unitários) está VERDE. Além disso:

  • Testing sub‑wave: 21 testes de borda extras, cobertura ~99% de linha nos módulos de repo/domínio, e 2 bugs reais encontrados e corrigidos (B1: acesso a lesson inexistente vira no-op seguro; B2: a quebra garante ≥2 filhas mesmo quando o breakPlan prevê 0/1 filhas).
  • Validation (gate assíncrono): VERDE.
  • E2E Playwright: não roda por-merge (política — roda apenas na validation e no gate final; aqui o gate final é a suíte unitária + build + lint).
O que “no-op seguro” significa (fix B1)?

recordAnswer e recordHintBreak, ao serem chamados para uma lesson inexistente, passam a não fazer nada (no-op) em vez de lançar erro — comportamento defensivo descoberto por um teste de borda.

O que “≥2 filhas mesmo com breakPlan 0/1” significa (fix B2)?

Se o plano de quebra calculasse 0 ou 1 sub-aula, a árvore não crescia. O fix garante que a quebra sempre produza pelo menos 2 filhas, mantendo a progressão em prática guiada.

11. Decisões autônomas da execução

  1. better-sqlite3 como SQL interno (nativo, DI-friendly, testável).
  2. Aula curta: maxParagraphs=2, ~80 palavras/parágrafo truncadas com ellipsis.
  3. “Aulas feitas” = answeredCount do assunto (soma de respostas), usada no rótulo “Continuar · N aulas feitas”.
  4. Botão primário: “Continuar” quando há aula pendente; “Gerar nova aula” quando não.
  5. Complexidade crescente via progressionDifficulty (baseline 1, aumenta com respostas, teto cap 5).
  6. Quebra de hint gera ≥2 sub-aulas (prática guiada) ligadas por parent/origin.
Convenção de onda (sub‑wave) que explica os nomes

A entrega caminha por “ondas” (onda1-sql, onda2-motor, onda3-ui/-arvore) seguidas de uma “testing sub‑wave” (com test-*) e “validation sub‑wave” (gate assíncrono). Cada entrega é um squash-commit descritivo.
