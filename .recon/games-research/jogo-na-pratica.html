Proposta prática · study-method · secção Games

O jogo na prática: como seria, tela a tela

Brief

Levar a proposta "híbrido com verificação" do plano de Games ao concreto: o loop de jogo real, um nível trabalhado de ponta a ponta em C/Python/Rust, as telas como ficam no app, o que se reutiliza da arquitetura existente e por onde começar a construir.

01

O loop em 60 segundos

O ciclo: escrever → testar → veredito por teste → escolher entre otimizar (replay) ou avançar

A grande diferença para os exercícios atuais das trilhas: passar não é o fim. Passar destrava o modo otimização (menos linhas? menos tempo?), e é aí que o jogo vicia: o histograma mostra onde a tua solução cai em relação às outras soluções daquele nível — comparação assíncrona, sem leaderboard obrigatória (a evidência manda colocar rankings fora da v1).

04

O que é um nível por baixo

Um nível é exatamente o objeto de desafio que o app já valida (enunciado + starter + solução de referência + requirements[] em bijeção com testes), acrescido de um bloco de jogo:

resources/games/mundo-1/nivel-3.json (reutiliza o schema de desafio + bloco game) 
{
  "title": "Rotear encomendas",
  "language": "c",                  // ou python/rust/… — mesma mecânica, adaptador troca
  "enunciado": "…",
  "starter": "int rota(int* p, int n) { /* … */ }",
  "reference": "…",               // solução que PASSA (prova 1 das 4)
  "requirements": [ /* 1:1 com os 6 testes */ ],
  "expectedTestCount": 6,
  "game": {
    "world": "mundo-1", "level": 3,
    "introduces": ["lacos", "arrays"],
    "optimize": {
      "lines": { "par": 12, "record": 9 },
      "time":  { "parMs": 2, "recordMs": 1 }
    }
  }
}

As 4 provas de execução que o autor já faz para desafios valem para níveis: referência passa · starter falha · contagem bate · stub vazio falha. O game só acrescenta métricas de otimização (medidas pelo mesmo runner: nº de linhas do ficheiro, tempo de execução).

05

Tela 3: o chefe de módulo

Prova final do módulo: junta tudo o que o módulo ensinou

Um desafio cumulativo (laços + arrays + funções, no nosso exemplo) com os mesmos testes rigorosos; passar desbloqueia o Mundo 2. O invólucro de "chefe" é leve e opcional (a evidência diz: o ganho real vem do teste cumulativo, não do teatro) — podes resolver com a barra de vida animada ou em modo "avaliação" simples. Sem ranking: o progresso é teu (delta pessoal é o sinal primário).

Evidência: avaliação cumulativa melhora retenção (±15 pp, heterogéneo); invólucro "boss" = motivação apenas

Formato concreto: problema integrador (ex.: "o robô do depósito completo: roteia, prioriza e gera o relatório final") com 8–10 testes, incluindo casos que só passam se o aluno dominar os 3 conceitos do módulo. O app já sabe fazer isto — é o "desafio final" das trilhas com mais requisitos.

06

Por onde começar (ordem de construção)

Passo 1

Vertical slice: 1 mundo, 4 níveis + 1 chefe, em UMA trilha

Novo painel Games (PanelKey + view), um jogo de demonstração em C, Python e Rust (mesmo mundo, 3 adaptações do mesmo enunciado), veredito por teste reutilizando o harness. É isto que prova o contrato multi-linguagem na prática.

games/mundo-1/*.jsonGameViewexec/harness
Passo 2

Modo otimização + histogramas locais

Métricas de linhas/tempo pelo runner, alvos por nível, distribuição guardada em disco, "Avançar" sempre disponível (resolver basta). Medir: quantas vezes o aluno repete por otimização — o indicador de que o loop vicia.

Passo 3

Chefe de módulo + desbloqueio por domínio

Prova cumulativa com mastery unlock; métrica de sucesso inclui transferência: tarefa nova sem invólucro de jogo (o ponto de falha da literatura — medir desde o piloto).

Depois

Épocas, mais mundos, arena de agentes

Só depois de o piloto mostrar conclusão + repetição + transferência. Leaderboards? Fora até haver decisão expressa (recomendação: nunca obrigatórias; pseudónimos + opt-out se entrarem).
